**Done 2026-09-26 (#23 — connect rate limit, SDD, plan `docs/plans/2026-09-26-issue-23-connect-rate-limit.md`):** `lib/connect.ts` `countRecentConnects` counts `connect_submissions` rows in the last rolling hour — no new table, no migration (`idx_connect_submissions_created_at` already covers the window). Limits: **5/hr per email** (case-insensitive), **10/hr per truncated IP**. Signed in → session email only (a shared network must not block a signed-in user); signed out → either key trips it. Over the limit behaves exactly like the honeypot: success message, no row, no email. The count fails open. The connect email-format regex now runs only for signed-out visitors — the session email already passed the identical regex at sign-in, and the seed user `dev@localhost` (no dot) was being rejected. `e2e/connect-rate-limit.spec.ts` (serial, self-cleaning) covers both keys and the signed-in IP exemption; each test was proven to fail with its guard removed. **Known limits, accepted:** the count-then-insert isn't atomic, so a scripted *parallel* burst gets past the limit (fix if it ever happens: conditional `INSERT … SELECT … WHERE (count) < ?` + `rowsAffected`); drops are visible only as `[connect] rate limited (email|ip)` in function logs. **Pre-existing, unfiled:** `truncateIp` mangles compressed IPv6 (`filter(Boolean)` drops the empty group, so `2001:db8::5` → `2001:db8:5::`), which now feeds the IP key.
